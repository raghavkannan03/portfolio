Problem

Campus-scale autonomous drone delivery needs a full stack (perception, mission logic, navigation, and precision landing) that a rotating student team can develop and test safely in simulation before flight.

Architecture

  • Hardware: Tarot T960 hexacopter, Jetson Orin Nano companion computer + Pixhawk 6C, Livox Mid-360 LiDAR, LTE connectivity for campus-wide operation
  • Localization: PX4's own state estimator, cross-checked against a persistent obstacle map built from LiDAR returns
  • Mission logic: a state machine I wrote in C++ (TAKEOFF → TRANSIT → DELIVER → RETURN → SEARCH → LAND); Nav2 supplies path plans only and never commands the aircraft directly
  • Navigation: Nav2 for path planning  ·  Landing: AprilTag precision landing
  • Middleware: uXRCE-DDS bridge (replaced deprecated MAVROS)

My contributions

  • Finalized the hexacopter hardware architecture and connectivity design
  • Replaced MAVROS with a direct PX4↔ROS 2 bridge and debugged the topic-versioning issues that came with it; a mismatched message definition drops data silently while the topic still shows up in every listing, which took a while to run down
  • Read the full flight stack, about 13,800 lines, line by line and fixed 12 defects before trusting it with the aircraft
  • Diagnosed a mid-flight loss of control from the flight controller's own raw log rather than the higher-level system logs, traced it to a commanded-heading rate problem, and fixed it with rate limiting
  • Vendored and brought up the driver for the real obstacle-avoidance LiDAR (Livox Mid-360), including its mount transform and network configuration
  • Verified companion-computer integration: Jetson ↔ Pixhawk over UART with PX4 topics streaming via uXRCE-DDS
  • Structured the team into navigation, landing, and electronics/mechanical subteams; training the incoming software lead

Results

This stack has flown a full delivery mission end to end in simulation, no failsafe triggered. See Drone Delivery for the mission profile.

What I'd change

I'd focus more on recruiting last year so I wasn't the main software person on the team. Spreading that load earlier would have let the navigation and landing subteams move faster without bottlenecking on me.
